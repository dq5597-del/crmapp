|---|---|---|

### 狀態流程


| 舊值 | 新值 |

| 完工 | 完工驗收 |
| 暫停 | 施工中 + `is_paused = true` |
| 取消 | 取消（不變） |

## 三、階段 2：專案領料／退料

### 3-1 FIFO 成本層設計

現有 `inventory_transactions` 每筆入庫已帶 `unit_cost`，只缺「這批還剩多少沒被領走」。

```sql
alter table inventory_transactions
  add column if not exists remaining_qty numeric(10,2);

-- 入庫筆：remaining_qty 初始 = quantity
-- 出庫筆：remaining_qty 為 null（不參與 FIFO 消耗）
```

**回填舊資料**：依產品把歷史入庫層由新到舊累加，直到等於目前 `stock_qty` 為止，較舊的層 `remaining_qty = 0`。此法保證回填後帳面數量與現有庫存一致。

### 3-2 領料時的 FIFO 演算法

```
輸入：product_id、需求數量 Q

1. 取該產品所有 remaining_qty > 0 的入庫層，依 created_at 由舊到新排序
2. 逐層扣減：
     take = min(層.remaining_qty, 剩餘需求)
     成本累計 += take × 層.unit_cost
     層.remaining_qty -= take
     剩餘需求 -= take
   直到剩餘需求 = 0
3. 若層耗盡但需求未滿 → 庫存不足，整筆交易 rollback 並回報
4. 寫入 material_issue_items.cost_detail（JSONB，記錄取用了哪幾層各多少）
5. 產生一筆 inventory_transactions 出庫（type = '出庫'，reference_no = 領料單號）
```

> **注意**：步驟 2 到 5 必須在同一個 Postgres function 內以交易執行，避免兩人同時領料造成成本層超領。建議實作為 `issue_material(p_issue_id uuid)` 的 plpgsql function，前端只呼叫它。

### 3-3 資料表

```sql
create table material_issues (
  id             uuid primary key default gen_random_uuid(),
  issue_no       text unique not null,        -- MI-YYMMDD-001（領料）／MR-YYMMDD-001（退料）
  issue_type     text not null default '領料' check (issue_type in ('領料','退料')),
  project_id     uuid not null references projects(id) on delete restrict,
  issue_date     date default current_date,
  issued_to      text,                        -- 領料人（工班／師傅）
  warehouse      text,                        -- 倉別（預留，多倉時用）
  status         text not null default '草稿' check (status in ('草稿','已確認','已作廢')),
  total_cost     numeric(14,2) default 0,     -- FIFO 計算後的實際成本
  notes          text,
  created_by     uuid references auth.users(id) on delete set null,
  created_at     timestamptz default now()
);

create table material_issue_items (
  id             uuid primary key default gen_random_uuid(),
  issue_id       uuid not null references material_issues(id) on delete cascade,
  seq_no         int,
  product_id     uuid not null references products(id) on delete restrict,
  quantity       numeric(10,2) not null,
  batch_no       text,                        -- 批號（本期實作）
  serial_no      text,                        -- 單件序號（預留，階段 6）
  unit_cost_avg  numeric(12,2),               -- FIFO 加權後的單位成本
  cost_amount    numeric(14,2),               -- quantity × unit_cost_avg
  cost_detail    jsonb,                       -- [{layer_id, qty, unit_cost}, ...]
  item_notes     text
);
```

### 3-4 退料

退料是領料的逆向：數量為正、`issue_type = '退料'`，入庫時**以原領料成本回沖**（從 `cost_detail` 反推），而非用當前進價，否則專案成本會失真。退料產生的入庫層 `remaining_qty` 一樣參與後續 FIFO。

### 3-5 狀態與庫存連動

| 動作 | 庫存效果 |
|---|---|
| 領料單存為草稿 | 不動庫存 |
| 領料單「已確認」 | 執行 FIFO 扣減，寫入庫存異動 |
| 領料單作廢 | 回沖成本層與庫存異動（沿用進貨單的差額調整模式） |

## 四、階段 3：施工與工時紀錄

現有 `project_crew` 記的是「這個人在這個專案總共幾天、日薪多少」，屬於彙總層。要算派工工時需要逐日明細。

```sql
create table project_work_logs (
  id           uuid primary key default gen_random_uuid(),
  project_id   uuid not null references projects(id) on delete cascade,
  crew_id      uuid references project_crew(id) on delete set null,
  work_date    date not null default current_date,
  member_kind  text not null default '員工',   -- 員工／協力廠商／臨時工
  name         text not null,
  hours        numeric(5,2) default 8,         -- 派工工時
  rate_type    text not null default '日薪'    -- 日薪／時薪／點工／外包計件
                 check (rate_type in ('日薪','時薪','點工','外包計件')),
  rate         numeric(12,2) default 0,
  cost         numeric(12,2) default 0,        -- 依 rate_type 計算
  work_item    text,                           -- 施工項目（配線／掛架／調校…）
  notes        text,
  created_at   timestamptz default now()
);
```

### 成本計算規則

| rate_type | 公式 |
|---|---|
| 日薪 | `rate × (hours / 8)` — 未滿 8 小時按比例 |
| 時薪 | `rate × hours` |
| 點工 | `rate`（一趟一價，與工時無關） |
| 外包計件 | `rate`（依合約金額，計入外包費用而非人工） |

`project_crew.days` 與 `cost` 改為由 `project_work_logs` 彙總後回寫，避免兩處手輸不一致。

## 五、階段 4：結算與請款拋轉

```sql
create table project_billings (
  id              uuid primary key default gen_random_uuid(),
  billing_no      text unique not null,        -- PB-YYMMDD-001
  project_id      uuid not null references projects(id) on delete restrict,
  billing_date    date default current_date,
  phase_name      text,                        -- 期別（第一期款／驗收款／保留款）
  progress_pct    numeric(5,2),                -- 本期認列驗收進度 %
  amount          numeric(14,2) not null,      -- 本期請款金額（未稅）
  tax_amount      numeric(14,2) default 0,
  total_amount    numeric(14,2),
  sales_order_id  uuid references sales_orders(id) on delete set null,  -- 拋轉後產生的銷貨單
  status          text not null default '待拋轉'
                    check (status in ('待拋轉','已拋轉','已作廢')),
  notes           text,
  created_at      timestamptz default now()
);
```

### 拋轉流程

```
專案（完工驗收）
  → 建立請款單 project_billings（填期別、進度%、金額）
  → 按「拋轉至銷貨」
      ├─ 產生 sales_orders（client_id 帶專案客戶，project_id 回填）
      ├─ 產生 sales_order_items（一筆：品名 = 專案名稱 + 期別）
      └─ 銷貨單狀態「已確認」→ 既有 auto-ledger 自動產生應收帳款
  → 請款單 status = 已拋轉，記錄 sales_order_id
```

**重點**：拋轉只做到銷貨單為止，應收帳款交給既有的 `ensureReceivableForSalesOrder` 處理，不另開一條帳務路徑。這樣專案請款與一般銷貨走同一套應收流程，對帳才不會分岔。

### 防重複拋轉

`sales_order_id is not null` 即視為已拋轉，按鈕鎖定。作廢請款單時同步作廢銷貨單與應收（比照進貨單作廢應付的做法）。

## 六、階段 5：專案損益分析表

### 公式

```
專案淨毛利 = 專案收入 − 材料成本 − 人工成本 − 外包費用 − 其他直接費用

專案收入   = Σ project_billings.amount（status = 已拋轉，未稅）
材料成本   = Σ material_issues.total_cost（領料）− Σ（退料）
人工成本   = Σ project_work_logs.cost（rate_type ≠ 外包計件）
外包費用   = Σ project_work_logs.cost（rate_type = 外包計件）
其他直接費用 = Σ accounting expenses（若支出記錄加 project_id，階段 5 一併補）
```

### 呈現

單一專案損益卡片 + 全專案排行表，兩者都對照預算：

| 項目 | 預算 | 實際 | 差異 | 達成率 |
|---|---|---|---|---|
| 合約金額／收入 | `contract_amount` | Σ 已拋轉請款 | | |
| 材料成本 | `budget_material` | Σ 領料淨額 | | |
| 人工成本 | `budget_labor` | Σ 工時成本 | | |
| 外包費用 | `budget_outsource` | Σ 外包計件 | | |
| **淨毛利** | 合約 − 三項預算 | 收入 − 三項實際 | | 毛利率 % |

超支欄位以紅字標示；毛利率低於設定門檻（建議 15%）整列預警。

實作為 Postgres View `v_project_pnl`，前端直接查詢，避免在瀏覽器端跑多表彙總。
